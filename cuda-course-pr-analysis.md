## Основные категории проблем

### 1. Bank Conflicts в Shared Memory

**Проблема**: Неэффективная организация shared memory, приводящая к конфликтам банков памяти.

**PR #18 (Konstantinov - Lab3: Sobel Operator)**

**Комментарий преподавателя**:
> "возможны bank conflicts + лишние транзакции к shared памяти.
> По строкам 18 байт - это не кратно типичной ширине банков (и warp-reads в 2D могут конфликтовать).
> Это не ошибка, но часто даёт заметный штраф."

**Проблемный код** (works/konstantinov_aa/lab3/src/sobel.cu:26):
```cuda
#define TILE_SIZE 16                     
#define BLOCK_SIZE (TILE_SIZE + 2)        // = 18

__global__ void sobel_kernel_tiled(...) {
    // Shared memory для тайла + границы для свёртки 3x3
    __shared__ unsigned char tile[BLOCK_SIZE][BLOCK_SIZE];  // 18x18
    
    // Проблема: 18 байт по строке не кратно 32, возникают bank conflicts
    // при одновременном доступе потоков warp'а к элементам одной строки
}
```

**Решение**: Добавить padding к размерности, чтобы избежать конфликтов:
```cuda
__shared__ unsigned char tile[BLOCK_SIZE][BLOCK_SIZE + 1];  // Padding +1
```

**PR #10 (Cherednikov - Lab2: Matrix Multiplication)**

**Комментарий преподавателя**:
> "Bank conflicts в shared будет)
> И где +1 к размерам тайла?"

**Проблемный код** (works/cherednikov-eo/lab_2/main.cu - начальная версия):
```cuda

__shared__ int tile_b[TILE][TILE];
```

**Исправленный код** (после правки):
```cuda
__shared__ int tile_a[TILE][TILE + 1];  // +1 для устранения bank conflicts
__shared__ int tile_b[TILE][TILE + 1];
```

### 2. Неэффективная Coalesced Memory Access

**Проблема**: Неоптимальная загрузка данных из глобальной памяти, приводящая к множественным транзакциям.

**PR #18 (Konstantinov - Lab3: Sobel Operator)**

**Комментарий преподавателя**:
> "Ты грузишь 16*16 элементов через stride цикл, из-за чего глобальные чтения получаются слабо коалесцированными (потоки варпа читают разбросанные адреса). много тут транзакций к памяти
> 
> Обычно лучше грузить так, чтобы threadIdx.x шёл последовательно по X в глобальной памяти"

**Проблемный код** (works/konstantinov_aa/lab3/src/sobel.cu:37):
```cuda
for (int i = linearIdx; i < totalPixels; i += numThreads) {
    // Преобразуем линейный индекс в 2D координаты внутри тайла
    int localY = i / BLOCK_SIZE;
    int localX = i % BLOCK_SIZE;
    
    // Глобальные координаты пикселя
    int globalX = tileStartX + localX;
    int globalY = tileStartY + localY;
    
    // Проблема: потоки с соседними threadIdx читают несоседние адреса памяти,
    // что ведет к неэффективным транзакциям
    if (globalX >= 0 && globalX < width && globalY >= 0 && globalY < height) {
        tile[localY][localX] = input[globalY * width + globalX];
    }
}
```

**Пояснение**: При таком подходе потоки одного warp'а читают данные с разных строк изображения, 
что приводит к большому количеству транзакций к глобальной памяти.

### 3. Некорректная реализация математических операций

**Проблема**: Использование неправильной формулы для вычисления магнитуды градиента.

**PR #18 (Konstantinov - Lab3: Sobel Operator)**

**Комментарий преподавателя**:
> "Это L1 норма, а не магнитуда)
> 
> Магнитуда считается по формулам sqrt квадратов"

**Проблемный код** (works/konstantinov_aa/lab3/src/sobel.cu:82):
```cuda
float gx = 0.0f;
float gy = 0.0f;

// ... вычисления градиентов ...

// Неправильно: это L1 норма (манхэттенское расстояние)
float magnitude = abs(gx) + abs(gy);
```

**Правильный вариант**:
```cuda
// Правильная магнитуда (L2 норма)
float magnitude = sqrtf(gx * gx + gy * gy);
```

### 4. Неправильные типы данных

**Проблема**: Использование типов, которые могут вызвать переполнение или неэффективность.

**PR #10 (Cherednikov - Lab2: Matrix Multiplication)**

**Комментарий преподавателя**:
> "Для acc может случиться переполнение - давай поправим тип acc."

**Проблемный код** (works/cherednikov-eo/lab_2/main.cu:95):
```cuda
__global__ void gpu_optimised_mm(...) {
    int acc = 0;  // Может переполниться при больших матрицах
    
    for (int t = 0; t < numTiles; ++t) {
        // ...
        for (int j = 0; j < TILE; ++j) {
            acc += tile_a[ty][j] * tile_b[j][tx];
        }
    }
}
```

**Исправленный код**:
```cuda
long long acc = 0;  // Предотвращает переполнение
```

**PR #18 (Konstantinov - Lab3: Sobel Operator)**

**Комментарий преподавателя**:
> "Зачем тогда gx, gy во float, если к нему плюсуется unsigned char * int?)"

**Проблемный код** (works/konstantinov_aa/lab3/src/sobel.cu:76):
```cuda
float gx = 0.0f;
float gy = 0.0f;

// Проблема: зачем float, если все операции с целыми числами?
for (int dy = -1; dy <= 1; dy++) {
    for (int dx = -1; dx <= 1; dx++) {
        unsigned char pixel = tile[ty + dy][tx + dx];
        int ky = dy + 1;
        int kx = dx + 1;
        gx += pixel * SOBEL_X[ky][kx];  // unsigned char * int -> int

    }
}
```

**Оптимальнее было бы**:
```cuda
int gx = 0;
int gy = 0;
// ... вычисления ...
float magnitude = sqrtf((float)(gx * gx + gy * gy));
```

## Общие рекомендации

### 1. Оптимизация Shared Memory
- Всегда добавляйте padding (+1) к размерности массивов в shared memory для избежания bank conflicts
- Размер строки в shared memory должен быть кратен размеру банка (обычно 32 байта)

### 2. Coalesced Memory Access
- При загрузке данных из глобальной памяти соседние потоки должны читать соседние адреса
- Используйте threadIdx.x для последовательного обхода по X координатам

### 3. Правильные типы данных
- Используйте достаточно большие типы для аккумуляторов (long long вместо int)
- Избегайте ненужных преобразований типов (float там, где достаточно int)

### 4. Математическая корректность
- Используйте правильные формулы (магнитуда = sqrt(x² + y²), а не |x| + |y|)
- Понимайте разницу между L1 и L2 нормами

### 5. Оформление PR
- Следуйте принятому в репозитории формату названий и описаний
- Проверяйте соответствие названия PR выполненной лабораторной работе
